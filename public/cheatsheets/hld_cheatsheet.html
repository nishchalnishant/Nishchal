    01HLD: requirements to architecture

    60-minute interview route#

    TimeFocus
    0–5Core use cases, constraints, invariants
    5–10Peak QPS, storage, bandwidth, retention
    10–15APIs and entities
    15–30Client → edge → services → stores
    30–50Deep-dive 2–3 workload risks
    50–60Failures, trade-offs, security, cost

    What interviewers score

    • Requirements: you ask before you draw, and write the numbers down.
    • Trade-offs: every choice names its cost and the alternative you rejected.
    • Bottlenecks: you find the hot path, hot key or fan-out before being asked.
    • Failure thinking: retries, idempotency, degradation and data loss are covered.
    • Communication: you drive the session, summarise and check in at each step.

    Keep the last 3–5 minutes to walk the design back against the requirements.

    Clarifying questions checklist New#

    AreaAskWhy it changes the design
    Users and scope (functional requirements)Who are the users? Which 3–5 actions matter? What is explicitly out of scope?Prevents designing features nobody asked for
    ScaleDAU, peak QPS, read:write ratio, data size today and in 3–5 yearsDecides single DB vs sharding, caching, async processing
    Latencyp50 and p99 targets for the main read and write pathsDecides caching, precomputation, regional deployment
    ConsistencyMust a user see their own write immediately? Can others see stale data, and for how long?Strong vs eventual consistency per operation
    AvailabilityTarget SLO; single region or multi-region; what happens during an outage?Replication, failover, degradation strategy
    DurabilityCan any data be lost? Retention period?Synchronous replication, backups, storage tiering
    Security and complianceAuthentication, sensitive data (PII, payments), data residencyEncryption, isolation, regional storage, audit logs
    Clients and accessWeb, mobile, third-party API? Offline support? Real-time updates?Protocols (REST, WebSocket, SSE), sync design
    Cost and constraintsBudget, team size, existing systems that must be reusedManaged services vs self-hosted; simplicity

    Every row after the first is a non-functional requirement (NFR): how well the system must do its job rather than what it does.

    Interview tip: write the answers as a short list on the board, then refer back to them when you justify each decision.

    Latency numbers#

    OpTime
    L1 cache0.5 ns
    Branch mispredict5 ns
    L2 cache7 ns
    Mutex lock/unlock25 ns
    Main memory100 ns
    Compress 1 KB (Snappy)3 µs

    Read 1 MB disk20 ms
    CA → Netherlands → CA150 ms

    Takeaways: memory is ~10× faster than SSD for sequential reads and ~106× faster than a cross-continent round trip. Avoid chatty cross-region calls; batch, cache, and keep hot data in memory.

    Storage, availability, sizes#

    ItemValue
    HDD IOPS100–200
    SATA SSD IOPS~90K
    NVMe IOPS500K–1M
    99.9%8.76 h/yr · 43.8 min/mo
    99.99%52.6 min/yr · 4.4 min/mo
    99.999%5.26 min/yr
    2^10 / 2^20 / 2^30 / 2^40KB / MB / GB / TB
    1 day~86,400 s ≈ 10^5 s
    1M req/day≈ 12 QPS (peak ×2–3)
    Snowflake ID41b ts + 10b machine + 12b seq = 4096 IDs/ms/node

    Estimation recipe#

    • QPS = DAU × actions/day ÷ 86,400; peak = 2–3× (consumer flash ≈ 12×)
    • Storage = writes/day × size × retention × replication (3×)
    • Bandwidth = QPS × payload
    • Cache = 20% of daily reads (80/20 rule)
    • Servers = peak QPS ÷ per-server QPS (~1–10K simple API)
    • State only the numbers that change a design choice
    Example: URL shortener
    • 100M new URLs/day → ~1.2K writes/s; 100:1 reads → ~120K reads/s
    • 500 B/row × 100M × 365 × 5y ≈ 90 TB
    • Base62, 7 chars → 62^7 ≈ 3.5 T keys

    Shortcuts

    • 1 day ≈ 105 s, so 1M requests/day ≈ 12 QPS and 100M/day ≈ 1.2K QPS.
    • 210 ≈ 103: 1 billion rows × 1 KB ≈ 1 TB.
    • One commodity server: ~10K simple QPS, 64–256 GB RAM, a few TB SSD.

    ChoicePick A when…Pick B when…
    CAP during a partitionReject or limit conflicting writes when invariants need strong consistency (e.g., balances, unique reservations)Accept writes and reconcile later when stale or duplicate state is tolerable (e.g., presence, some feed signals)
    SQL vs NoSQLjoins, transactions, ad-hoc querieshuge scale, simple access, flexible schema
    Sync vs asyncuser waits for resultslow / fan-out / retryable work
    Push vs pullfew followers, real-timecelebrities, inactive users
    Horizontal vs verticalunbounded growth, HAsimple, early stage
    Monolith vs microsmall team, earlyindependent scaling / teams
    Stateful vs statelessWebSocket sessionsAPI tier (scale freely)
    Normalise vs denormalisewrite-heavy, consistencyread-heavy, avoid joins
    Latency vs throughputuser-facingbatch / analytics

    ConceptShows up in

    Reliability toolkit#

    • Idempotency keys on every retryable write
    • Retries w/ exponential backoff + jitter; circuit breaker; timeouts
    • Outbox pattern (avoid dual-write); saga with compensations
    • Leader election (Raft / ZooKeeper); quorum R+W>N
    • Back-pressure, DLQs, rate limits, graceful degradation
    • Observability: metrics, logs, traces; SLO / error budgets

    Caching failure modes New#

    ProblemWhat happensFix
    Stampede (thundering herd)A hot key expires; thousands of requests hit the database at onceRequest coalescing or a per-key lock; refresh ahead of expiry; serve stale while revalidating
    PenetrationRequests for keys that don't exist always miss and hit the database (often an attack)Cache negative results with a short TTL; Bloom filter of valid keys; validate input
    AvalancheMany keys expire at the same moment, or the cache cluster restarts coldAdd random jitter to TTLs; warm the cache before traffic; replicate the cache
    Hot keyOne key's traffic exceeds a single cache nodeLocal in-process cache; split the key into copies (key#1..n); CDN for public data
    Big keyA huge value blocks the node and the networkSplit into pages or fields; compress; store the blob elsewhere and cache a pointer
    Stale or inconsistent dataCache and DB disagree after concurrent writesDelete-on-write after the DB commit, short TTLs, versioned keys, CDC-driven invalidation
    Cache pollutionOne-off scans evict genuinely hot dataAdmission policies (TinyLFU), don't cache bulk reads

    Little's law and utilisation#

    L = λ × Win-flight requests = arrival rate × latency1,000 req/s × 0.2 s = 200 concurrent requests
    • Queueing delay grows sharply past ~70–80% utilisation; plan headroom.
    • Fan-out multiplies tail latency: 100 calls each with 1% slow → 63% of requests hit a slow one.
    • Thread-pool size ≈ throughput × latency (per instance).

    Proxy, gateway, load balancer, mesh: who does what New#

    05Databases and storage internals

    What you need to justify a data-store choice and to answer "how does it scale" and "what anomalies can happen".

    Index and storage engines#

    StructureGood atCostSeen in
    B+ treePoint and range reads; in-place updatesRandom writes, page splitsPostgres, MySQL InnoDB
    LSM tree (memtable → SSTables)High write throughput; sequential I/ORead and space amplification; compactionCassandra, RocksDB, LevelDB
    Hash indexO(1) point lookupNo rangesRedis, Bitcask
    Inverted indexFull-text searchIndex build and update lagElasticsearch, Lucene
    Geo indexNearby queriesCell-size tuningGeohash, quadtree, S2, H3, R-tree
    Vector indexApproximate nearest neighboursRecall vs memory vs latencyHNSW, IVF-PQ
    Bitmap / columnarAnalytics filters and scansSlow single-row updatesDruid, ClickHouse, Parquet
    Composite index: leftmost-prefix rule. Put equality columns first, range column last. Covering index avoids table lookups.

    Isolation levels and anomalies#

    LevelPreventsStill allows
    Read uncommitted—Dirty reads
    Read committed (Postgres default)Dirty readsNon-repeatable reads, lost updates
    Repeatable read / snapshot (MySQL default)Non-repeatable readsWrite skew (phantoms depend on engine)
    Serializable (2PL or SSI)All of the aboveLower throughput, retries on conflict
    • Lost update fix: SELECT … FOR UPDATE, atomic UPDATE … SET x = x - 1 WHERE x > 0, or optimistic version column.
    • Write skew (two doctors both go off call): needs serializable or a constraint/lock on the shared predicate.
    • ACID vs BASE: atomicity, consistency, isolation, durability vs basically available, soft state, eventually consistent.

    Replication#

    ModeProsCons
    Single leaderSimple; no write conflictsLeader is the write bottleneck; failover risk
    Multi-leaderMulti-region writes; offline clientsConflict resolution (LWW, CRDT, app merge)
    Leaderless (Dynamo)High availability; tunable quorumRead repair, hinted handoff, sloppy quorums
    SynchronousNo data loss on failoverLatency; blocked by slow replica
    AsynchronousFast writesReplication lag; possible loss on failover
    Replication-lag fixes: read-your-writes (read own data from leader or wait for LSN), monotonic reads (pin user to one replica), consistent prefix (same partition order).

    Partitioning (sharding)#

    StrategyGood forWatch out
    RangeRange scans, time seriesHot latest partition
    HashEven spreadNo range queries; resharding moves data
    Consistent hash + vnodesElastic clustersOnly ~K/N keys move on change
    Directory / lookupFlexible placement, tenant movesLookup service is critical path
    Geo / tenantData residency, isolationUneven tenant sizes
    • Hot key: add a random suffix (key#0..n) and merge on read; or cache it locally.
    • Secondary index: local (scatter-gather reads) vs global (async, partitioned by term).
    • Cross-shard transactions are expensive: choose the shard key so most transactions stay on one shard.

    Picking a data model#

    QuestionIf yes
    Need multi-row transactions or strong constraints (money, inventory)?Relational; keep the invariant in one DB
    Access is always by a known key at huge scale?Key-value / wide-column; model one table per query
    Entity is a self-contained, evolving document?Document store
    Queries traverse relationships many hops deep?Graph DB (or adjacency lists + cache if shallow)
    Append-only measurements over time?Time-series DB with downsampling and retention
    Free-text relevance or facets?Search index fed by CDC from the source of truth
    Semantic similarity?Vector index (pgvector to start; dedicated store at 10M+ vectors)

    07Worked designs: eight full walkthroughs

    Five classic prompts carried through the 60-minute route: requirements, estimates, API and data model, architecture, deep dives and trade-offs. Use them as model answers to rehearse out loud.

    URL shortener#

    Read-heavy key lookup. The interesting parts are generating short unique codes and keeping redirects under ~50 ms at 100K+ QPS.

    flowchart LR
  C["Client"] --> CDN["CDN edge"]
  CDN --> LB["Load balancer"]
  LB --> R["Redirect service"]
  LB --> W["Create service"]
  R --> RC[("Redis<br/>code → URL")]
  R --> DB[("KV store: urls")]
  W --> IDG["ID range allocator"]
  W --> DB
  R -.->|"click event"| K[["Kafka"]]
  K -.-> AN[("Analytics store")]

    Requirements

    • Shorten a URL to a 7-character code; redirect; optional custom alias and expiry; click analytics.
    • 100M new URLs/day, 100:1 read:write, p99 redirect < 50 ms, highly available.

    Back-of-envelope

    writes ≈ 100M / 86,400 ≈ 1.2K/s (peak ~3K)reads ≈ 120K/s (peak ~350K)storage ≈ 500 B × 100M × 365 × 5 y ≈ 90 TBbase62, 7 chars → 62⁷ ≈ 3.5 trillion codes

    API and data model

    POST /v1/urls  {long_url, alias?, ttl_days?}  → 201 {code}
GET  /{code}   → 302 Location: long_url

urls(code PK, long_url, owner_id, created_at, expires_at)
click events → Kafka → analytics (OLAP)

    Deep dives

    • Code generation: each server leases a counter range (e.g. 1M IDs) from a coordinator, base62-encodes, and scrambles with a bijection so codes aren't guessable. No collision checks needed.
    • Read path: CDN caches popular redirects briefly; Redis LRU for hot codes; KV store partitioned by code hash.
    • Custom alias: conditional put (insert if absent) gives uniqueness.
    • Expiry: store TTL; check on read; background cleanup.

    Trade-offs

    • 301 is cached by browsers (less load, lost analytics); 302 keeps every click visible.
    • Hash of URL + collision retry avoids coordination but costs extra reads.
    • Abuse: scan destinations, rate-limit creators.

    News feed (home timeline)#

    Write fan-out versus read fan-out. The celebrity problem decides the design, so raise it before the interviewer does.

    flowchart LR
  U["Client"] --> API["API gateway"]
  API --> PS["Post service"]
  PS --> PDB[("Posts DB")]
  PS --> K[["Kafka: new posts"]]

    Ticket booking with flash sales#

    Payment system New#

    Money must never be created, lost or double-charged. Idempotency, a double-entry ledger and reconciliation carry the design.

    Kafka partitions and consumer groups#

    flowchart LR
  P["Producers<br/>partition = hash(key)"] --> T0["Partition 0"]
  P --> T1["Partition 1"]
  P --> T2["Partition 2"]
  T0 --> C1["Group A: consumer 1"]

    Order holds within a partition. In a group, each partition goes to one consumer, so consumers beyond the partition count sit idle. Separate groups read independently.

    • Health: watch consumer lag per partition; rising lag means scale consumers or fix a slow handler.

    09Consistency, consensus and time

    The distributed-systems theory interviewers dig into at senior levels, condensed to what changes a design.

    Consistency models, strongest first#

    ModelGuaranteeExample
    LinearizableEvery read sees the latest write; real-time orderetcd, Spanner, single-leader sync reads
    SequentialOne global order consistent with each client's orderZooKeeper writes
    CausalCause precedes effect everywhereComment shows after the post it replies to
    Read-your-writesYou see your own updatesProfile edit visible immediately
    Monotonic readsNever go back in timePin session to a replica
    EventualReplicas converge if writes stopDNS, likes counters, Dynamo defaults

    CAP and PACELC#

    • CAP: during a network partition, choose consistency (reject some requests) or availability (serve possibly stale data). Partitions are not optional.
    • PACELC: if Partition → A or C; Else → Latency or Consistency. Even without failures, strong consistency costs latency.
    SystemPACELC
    DynamoDB, Cassandra (default)PA / EL
    Spanner, CockroachDB, etcdPC / EC
    MongoDB (majority)PC / EC (tunable)
    Quorum: N replicas, write W, read R. R + W > N gives overlapping sets (N=3, W=2, R=2). Choose per operation.

    Consensus and leadership#

    • Raft: leader election with terms and randomised timeouts; leader appends entries; commit when a majority acknowledges; 2f+1 nodes tolerate f failures.
    • Paxos / Multi-Paxos: same safety guarantees, harder to explain; ZAB in ZooKeeper.
    • Leases give a leader time-bounded authority; require bounded clock drift.
    • Fencing tokens: monotonically increasing token checked by storage, so a paused old leader can't write after losing its lock.
    • Split brain: prevented by majority quorums; never run 2-node clusters without a tiebreaker.
    • Use consensus for metadata (who is leader, config, locks), not for every data write.

    Time, ordering and failure detection#

    ToolUse
    Physical clocks (NTP)Drift ms–100s of ms; don't order events across machines with them
    Lamport clockTotal order consistent with causality (counter max+1)
    Vector clockDetect concurrent writes (siblings) in leaderless stores
    Hybrid logical clockPhysical time + logical counter (CockroachDB)
    TrueTimeBounded uncertainty; Spanner waits it out for external consistency
    Heartbeats + timeoutsSimple failure detection; tune to avoid flapping
    GossipMembership and state spread in O(log N) rounds
    Phi-accrual detectorSuspicion level instead of binary up/down (Cassandra)

    Distributed transactions: choosing the tool#

    ApproachHowUse whenDownside
    Single-DB transactionKeep related data on one shard/DBAlways try firstConstrains data model
    Two-phase commitCoordinator: prepare → commitInside one database system (Spanner, XA)Blocking if coordinator dies; latency
    Saga (orchestrated)Central workflow runs steps + compensationsMulti-service business flows (order → payment → shipping)No isolation; design compensations
    Saga (choreographed)Services react to each other's eventsFew steps, loosely coupled teamsHard to trace the overall flow
    Transactional outboxWrite row + event in one local txn; relay publishesDB update must emit an event reliablyRelay adds delay; consumers dedupe
    TCC (try-confirm-cancel)Reserve resources, then confirm or cancelInventory, bookings, payments holdsEvery service implements three APIs

    CRDTs and conflict resolution#

    • Last-write-wins: simple, silently drops concurrent updates.
    • CRDTs: merge automatically without coordination: G-counter, PN-counter, OR-set, LWW-register, RGA/sequence CRDTs for collaborative text.
    • Operational transform: classic Google Docs approach; needs a central server to order operations.
    • Application merge: keep siblings and let the domain decide (shopping cart union).

    Distributed locks done right New#

    OptionHowCaveat
    Database lockSELECT … FOR UPDATE, advisory locks, or a unique row as the lockSimple and correct if you already depend on that database
    Redis single nodeSET key token NX PX 30000; release with a Lua script that checks the tokenLost on failover before replication; fine for efficiency, not for correctness
    Redlock (several Redis nodes)Acquire on a majority of independent nodes within a time limitRelies on timing assumptions; disputed for correctness-critical use
    ZooKeeper / etcdEphemeral (lease-backed) nodes; the lowest sequence number holds the lockConsensus-backed and safe; more operational weight

    • Leases expire: GC pauses or network delays can outlast the lease; never assume you still hold it without fencing.
    • Prefer avoiding locks: single-writer partitions, conditional writes (UPDATE … WHERE version = ?), and idempotent operations often remove the need entirely.

    API design checklist#

    • Large uploads: pre-signed URL direct to object storage; resumable/multipart.
    • Long jobs: 202 Accepted + status endpoint or webhook.

    Security checklist#

    • TLS everywhere; encrypt at rest (KMS, envelope encryption).
    • Secrets in a vault, never in code or images.
    • Input validation; parameterised queries (SQL injection); output encoding (XSS).
    • CSRF tokens; SSRF allow-lists for server-side fetches.
    • WAF, rate limits and CDN absorb DDoS.
    • Least privilege IAM; audit logs for sensitive access.
    • PII: minimise, tokenise, regional storage, deletion workflows (GDPR/DPDP).
    • Payments: tokenise cards; stay out of PCI scope.

    OAuth 2.0 authorization code with PKCE#

    sequenceDiagram
  participant A as App
  participant AS as Auth server
  participant API as Resource API
  A->>A: make code_verifier and code_challenge = SHA256(verifier)
  A->>AS: /authorize with code_challenge
  Note over AS: user signs in and consents
  AS-->>A: redirect with authorization code
  A->>AS: /token with code + code_verifier
  AS-->>A: access token + refresh token
  A->>API: request with Bearer access token
  API-->>A: data

    PKCE stops a stolen authorization code from being exchanged: only the app holding the verifier can redeem it.

    Multi-tenancy New#

    ModelIsolationCost and effortFits
    Pool (shared everything)tenant_id on every row, row-level security, per-tenant quotasCheapest, simplest to operateMany small tenants
    Bridge (shared app, separate schemas or databases)Data separated per tenant; compute sharedModerate; migrations run per schemaMid-size tenants, compliance needs
    Silo (dedicated stack or cell)Full isolation per tenantMost expensiveLarge or regulated customers

    • Security: enforce the tenant in every query (row-level security), per-tenant encryption keys for sensitive customers.
    • Operations: tenant-aware logging, metrics and billing; tenant-level backups and data export or deletion.

    14Follow-up questions and strong answers

    The curveballs asked after the main design. A good answer names the mechanism, the trade-off and the number.

    Curveball → answer#

    They askStrong answer
    Traffic grows 10×. What breaks first?Walk the path: DB writes (shard or queue), cache hit ratio, hot keys, connection pools. Autoscale stateless tiers; add read replicas; precompute.
    One key gets 1M QPS (celebrity, flash sale)Local in-process cache with short TTL, key splitting with merge on read, request coalescing, CDN for public data.
    A whole region goes downHealth checks + global LB/DNS failover; replicated data with known RPO; idempotent replays; degrade non-critical features.
    How do you avoid double charging?Idempotency key stored with the result; payment state machine; reconcile with the provider; treat timeout as "unknown", not failure.
    Exactly-once processing?At-least-once delivery + idempotent consumer or dedup table; Kafka transactions for read-process-write within Kafka.
    Migrate a live database with no downtimeExpand–contract: dual write, backfill, verify with shadow reads, switch reads, stop old writes, remove.
    Counts are wrong under concurrency (likes, views)Atomic increments or sharded counters; batch flush to DB; HyperLogLog for unique counts.
    Cache and DB disagreeCache-aside with delete-on-write, short TTL, versioned keys, or CDC-driven invalidation.
    Queue consumers fall behindScale consumers up to partition count; increase partitions; batch; DLQ poison messages; back-pressure producers.
    Latency p99 is bad, p50 fineFind fan-out and GC pauses; hedged requests; timeouts per hop; cache warmers; reduce payload size.
    Schema change across many servicesBackward-compatible changes (add optional fields), schema registry, consumers before producers.
    How would you test this?Load tests at 2× peak, chaos experiments (kill nodes, inject latency), game days, canaries with automatic rollback.
    What does it cost?Estimate the dominant item (storage, egress, GPU, DB IOPS); tiered storage; reserved capacity; cache to cut origin load.

    15HLD last-minute checklist

    HLD last-minute checklist#

    • State users, core actions, and the invariant to preserve.
    • Estimate only numbers that change the architecture.
    • Show read and write paths; mark sync and async boundaries.
    • Explain cache freshness, shard key, hot-key plan, consistency.
    • Make retries safe; treat timeouts as unknown outcomes.
    • Cover overload, dependency failure, regional recovery, degradation.
    • Name SLO, observability, security, rollout, and rollback.
    • For each choice: alternative → reason → failure mode.
