    Checklist before you write code

    • Every mutable field has exactly one owning class.
    • Invariants are checked inside constructors and methods, not by callers.
    • Interfaces sit at the seams you will swap or fake: clock, ID generator, payment, storage.
    • For each shared object, name the lock or atomic that guards it.
    • Expected failures are domain exceptions; programming errors fail fast.

    60-minute interview route#

    TimeFocus
    0–5Core use cases, constraints, invariants
    5–10Peak QPS, storage, bandwidth, retention

    What interviewers score

    • Requirements: you ask before you draw, and write the numbers down.
    • Trade-offs: every choice names its cost and the alternative you rejected.
    • Bottlenecks: you find the hot path, hot key or fan-out before being asked.
    • Failure thinking: retries, idempotency, degradation and data loss are covered.
    • Communication: you drive the session, summarise and check in at each step.

    Keep the last 3–5 minutes to walk the design back against the requirements.

    Estimation recipe#

    • QPS = DAU × actions/day ÷ 86,400; peak = 2–3× (consumer flash ≈ 12×)
    • Storage = writes/day × size × retention × replication (3×)
    • Bandwidth = QPS × payload
    • Cache = 20% of daily reads (80/20 rule)
    • Servers = peak QPS ÷ per-server QPS (~1–10K simple API)
    • State only the numbers that change a design choice
    Example: URL shortener
    • 100M new URLs/day → ~1.2K writes/s; 100:1 reads → ~120K reads/s
    • 500 B/row × 100M × 365 × 5y ≈ 90 TB
    • Base62, 7 chars → 62^7 ≈ 3.5 T keys

    Shortcuts

    • 1 day ≈ 105 s, so 1M requests/day ≈ 12 QPS and 100M/day ≈ 1.2K QPS.
    • 210 ≈ 103: 1 billion rows × 1 KB ≈ 1 TB.
    • One commodity server: ~10K simple QPS, 64–256 GB RAM, a few TB SSD.

    Caching failure modes New#

    ProblemWhat happensFix
    Stampede (thundering herd)A hot key expires; thousands of requests hit the database at onceRequest coalescing or a per-key lock; refresh ahead of expiry; serve stale while revalidating

    Little's law and utilisation#

    L = λ × Win-flight requests = arrival rate × latency1,000 req/s × 0.2 s = 200 concurrent requests
    • Queueing delay grows sharply past ~70–80% utilisation; plan headroom.
    • Fan-out multiplies tail latency: 100 calls each with 1% slow → 63% of requests hit a slow one.
    • Thread-pool size ≈ throughput × latency (per instance).

    06Databases and storage internals

    What you need to justify a data-store choice and to answer "how does it scale" and "what anomalies can happen".

    Index and storage engines#

    StructureGood atCostSeen in
    B+ treePoint and range reads; in-place updatesRandom writes, page splitsPostgres, MySQL InnoDB
    LSM tree (memtable → SSTables)High write throughput; sequential I/ORead and space amplification; compactionCassandra, RocksDB, LevelDB
    Hash indexO(1) point lookupNo rangesRedis, Bitcask
    Inverted indexFull-text searchIndex build and update lagElasticsearch, Lucene
    Geo indexNearby queriesCell-size tuningGeohash, quadtree, S2, H3, R-tree
    Vector indexApproximate nearest neighboursRecall vs memory vs latencyHNSW, IVF-PQ
    Bitmap / columnarAnalytics filters and scansSlow single-row updatesDruid, ClickHouse, Parquet
    Composite index: leftmost-prefix rule. Put equality columns first, range column last. Covering index avoids table lookups.

    Isolation levels and anomalies#

    LevelPreventsStill allows
    Read uncommitted—Dirty reads
    Read committed (Postgres default)Dirty readsNon-repeatable reads, lost updates
    Repeatable read / snapshot (MySQL default)Non-repeatable readsWrite skew (phantoms depend on engine)
    Serializable (2PL or SSI)All of the aboveLower throughput, retries on conflict
    • Lost update fix: SELECT … FOR UPDATE, atomic UPDATE … SET x = x - 1 WHERE x > 0, or optimistic version column.
    • Write skew (two doctors both go off call): needs serializable or a constraint/lock on the shared predicate.
    • ACID vs BASE: atomicity, consistency, isolation, durability vs basically available, soft state, eventually consistent.

    Replication#

    ModeProsCons
    Single leaderSimple; no write conflictsLeader is the write bottleneck; failover risk
    Multi-leaderMulti-region writes; offline clientsConflict resolution (LWW, CRDT, app merge)
    Leaderless (Dynamo)High availability; tunable quorumRead repair, hinted handoff, sloppy quorums
    SynchronousNo data loss on failoverLatency; blocked by slow replica
    AsynchronousFast writesReplication lag; possible loss on failover
    Replication-lag fixes: read-your-writes (read own data from leader or wait for LSN), monotonic reads (pin user to one replica), consistent prefix (same partition order).

    Partitioning (sharding)#

    StrategyGood forWatch out
    RangeRange scans, time seriesHot latest partition
    HashEven spreadNo range queries; resharding moves data
    Consistent hash + vnodesElastic clustersOnly ~K/N keys move on change
    Directory / lookupFlexible placement, tenant movesLookup service is critical path
    Geo / tenantData residency, isolationUneven tenant sizes
    • Hot key: add a random suffix (key#0..n) and merge on read; or cache it locally.
    • Secondary index: local (scatter-gather reads) vs global (async, partitioned by term).
    • Cross-shard transactions are expensive: choose the shard key so most transactions stay on one shard.

    QuestionIf yes

    Queries traverse relationships many hops deep?Graph DB (or adjacency lists + cache if shallow)
    Append-only measurements over time?Time-series DB with downsampling and retention

    URL shortener#

    Read-heavy key lookup. The interesting parts are generating short unique codes and keeping redirects under ~50 ms at 100K+ QPS.

    writes ≈ 100M / 86,400 ≈ 1.2K/s (peak ~3K)reads ≈ 120K/s (peak ~350K)storage ≈ 500 B × 100M × 365 × 5 y ≈ 90 TBbase62, 7 chars → 62⁷ ≈ 3.5 trillion codes

    CAP and PACELC#

    • CAP: during a network partition, choose consistency (reject some requests) or availability (serve possibly stale data). Partitions are not optional.
    • PACELC: if Partition → A or C; Else → Latency or Consistency. Even without failures, strong consistency costs latency.
    SystemPACELC
    DynamoDB, Cassandra (default)PA / EL
    Spanner, CockroachDB, etcdPC / EC
    MongoDB (majority)PC / EC (tunable)
    Quorum: N replicas, write W, read R. R + W > N gives overlapping sets (N=3, W=2, R=2). Choose per operation.

    Consensus and leadership#

    • Raft: leader election with terms and randomised timeouts; leader appends entries; commit when a majority acknowledges; 2f+1 nodes tolerate f failures.
    • Paxos / Multi-Paxos: same safety guarantees, harder to explain; ZAB in ZooKeeper.
    • Leases give a leader time-bounded authority; require bounded clock drift.
    • Fencing tokens: monotonically increasing token checked by storage, so a paused old leader can't write after losing its lock.
    • Split brain: prevented by majority quorums; never run 2-node clusters without a tiebreaker.
    • Use consensus for metadata (who is leader, config, locks), not for every data write.

    API design checklist#

    • Nouns for resources, HTTP verbs for actions: POST /orders, GET /orders/{id}.
    • Idempotency: GET/PUT/DELETE by definition; POST needs an Idempotency-Key header.
    • Cursor pagination (?after=…&limit=50) over offset at scale.
    • Versioning: URL (/v2) or header; never break existing clients.
    • Consistent error body: code, message, details, request ID.
    • Status codes: 400 bad input, 401 unauthenticated, 403 forbidden, 404, 409 conflict, 429 rate-limited, 5xx server.
    • Rate-limit headers and Retry-After.
    • Large uploads: pre-signed URL direct to object storage; resumable/multipart.
    • Long jobs: 202 Accepted + status endpoint or webhook.
    • ETags for caching and optimistic concurrency (If-Match).

    Curveball → answer#

    They askStrong answer
    Traffic grows 10×. What breaks first?Walk the path: DB writes (shard or queue), cache hit ratio, hot keys, connection pools. Autoscale stateless tiers; add read replicas; precompute.

    Exactly-once processing?At-least-once delivery + idempotent consumer or dedup table; Kafka transactions for read-process-write within Kafka.

    Design principles beyond SOLID#

    • Composition over inheritance: assemble behaviour from parts; avoids fragile base classes.
    • Tell, don't ask: account.withdraw(x) rather than reading balance and deciding outside.
    • Law of Demeter: talk to direct collaborators only; avoid a.getB().getC().do().
    • DRY · KISS · YAGNI: no duplicated knowledge, simplest design that works, no speculative features.
    • High cohesion, low coupling: related behaviour together; few, narrow dependencies.
    • Program to interfaces; keep the domain free of framework and I/O code.
    • Immutability for value objects and anything shared across threads.
    • Fail fast: validate at construction; make illegal states unrepresentable (enums, types).

    State machine (vending machine)#

    interface State {
    default void insertCoin(Machine m, int c){ throw new IllegalStateException(); }
    default void select(Machine m, String code){ throw new IllegalStateException(); }
    default void dispense(Machine m){ throw new IllegalStateException(); }
}
class Idle implements State {
    public void insertCoin(Machine m, int c){ m.addBalance(c); m.setState(new HasMoney()); }
}
class HasMoney implements State {
    public void insertCoin(Machine m, int c){ m.addBalance(c); }
    public void select(Machine m, String code){
        if (!m.inventory().available(code)) throw new OutOfStock(code);
        if (m.balance() < m.price(code)) throw new InsufficientFunds();
        m.setSelection(code); m.setState(new Dispensing());
    }
}
class Dispensing implements State {
    public void dispense(Machine m){ m.release(); m.returnChange(); m.setState(new Idle()); }
}
// Illegal transitions fail loudly; no if/else on a status enum

    LRU cache, O(1) (Python)#

    class Node:
    __slots__ = ("k", "v", "prev", "next")
    def __init__(self, k=0, v=0): self.k, self.v, self.prev, self.next = k, v, None, None

class LRUCache:
    def __init__(self, cap):
        self.cap, self.map = cap, {}
        self.head, self.tail = Node(), Node()          # sentinels
        self.head.next, self.tail.prev = self.tail, self.head
    def _remove(self, n): n.prev.next, n.next.prev = n.next, n.prev
    def _add_front(self, n):
        n.next, n.prev = self.head.next, self.head
        self.head.next.prev = n; self.head.next = n
    def get(self, k):
        if k not in self.map: return -1
        n = self.map[k]; self._remove(n); self._add_front(n); return n.v
    def put(self, k, v):
        if k in self.map: self._remove(self.map[k])
        n = self.map[k] = Node(k, v); self._add_front(n)
        if len(self.map) > self.cap:
            lru = self.tail.prev; self._remove(lru); del self.map[lru.k]

    Token-bucket rate limiter (Java, thread-safe)#

    final class TokenBucket {
    private final long capacity; private final double refillPerNano;
    private double tokens; private long last;
    private final Clock clock;                       // injectable for tests
    TokenBucket(long cap, double perSec, Clock c){
        capacity = cap; refillPerNano = perSec / 1e9; tokens = cap; clock = c; last = c.nanos();
    }
    synchronized boolean tryAcquire(){
        long now = clock.nanos();
        tokens = Math.min(capacity, tokens + (now - last) * refillPerNano);  // lazy refill
        last = now;
        if (tokens < 1) return false;
        tokens -= 1; return true;
    }
}
class RateLimiter {
    private final ConcurrentHashMap<String, TokenBucket> buckets = new ConcurrentHashMap<>();
    boolean allow(String client){
        return buckets.computeIfAbsent(client, k -> new TokenBucket(10, 5, Clock.SYSTEM)).tryAcquire();
    }
}

    Variants and follow-ups

    • Leaky bucket smooths output to a fixed rate; fixed window is simple but bursts at window edges.
    • Sliding log is exact but stores every timestamp; sliding window counter approximates it with two counters.
    • Distributed: keep the bucket in Redis and refill-and-take in one Lua script so it stays atomic.
    • Memory: per-client buckets need eviction (expire idle keys).
    • Response: return 429 with Retry-After computed from the token deficit.

    Tic-tac-toe with O(1) win check (Java) New#

    final class TicTacToe {
    private final int n;
    private final int[] rows, cols;
    private int diag, anti;
    TicTacToe(int n) { this.n = n; rows = new int[n]; cols = new int[n]; }

    /** player 1 or 2; returns the winner or 0. */
    int move(int r, int c, int player) {
        int d = player == 1 ? 1 : -1;
        rows[r] += d; cols[c] += d;
        if (r == c) diag += d;
        if (r + c == n - 1) anti += d;
        int target = d * n;
        return (rows[r] == target || cols[c] == target || diag == target || anti == target) ? player : 0;
    }
}

    final class Topic {
    private final List<String> log = new CopyOnWriteArrayList<>();      // append-only

final class Subscriber implements Runnable {
    private final Topic topic; private final Consumer<String> handler;
    private final AtomicInteger offset = new AtomicInteger();             // own position
    private volatile boolean running = true;
    Subscriber(Topic t, Consumer<String> h) { topic = t; handler = h; }
    public void run() {
        while (running) {
            String m = topic.read(offset.get());
            if (m == null) { LockSupport.parkNanos(1_000_000); continue; }    // or wait/notify
            handler.accept(m);
            offset.incrementAndGet();                                    // commit after handling
        }
    }
    void resetOffset(int o) { offset.set(o); }                           // replay
    void stop() { running = false; }
}

    Elevator scheduling (LOOK)

    enum Direction { UP, DOWN, IDLE }

final class Elevator {
    private int floor = 0;
    private Direction dir = Direction.IDLE;
    private final TreeSet<Integer> up = new TreeSet<>(), down = new TreeSet<>();

    synchronized void addStop(int f) {
        if (f > floor) up.add(f); else if (f < floor) down.add(f);
        if (dir == Direction.IDLE && f != floor) dir = f > floor ? Direction.UP : Direction.DOWN;
    }
    synchronized void step() {                  // one tick = one floor
        if (dir == Direction.UP) {
            if (up.isEmpty()) { dir = down.isEmpty() ? Direction.IDLE : Direction.DOWN; return; }
            floor++;
            if (up.remove(floor)) openDoors();
        } else if (dir == Direction.DOWN) {
            if (down.isEmpty()) { dir = up.isEmpty() ? Direction.IDLE : Direction.UP; return; }
            floor--;
            if (down.remove(floor)) openDoors();
        }
    }
    synchronized int cost(int f, Direction d) {   // lower is better
        int dist = Math.abs(floor - f);
        if (dir == Direction.IDLE) return dist;
        boolean onTheWay = (dir == Direction.UP && d == Direction.UP && f >= floor)
                        || (dir == Direction.DOWN && d == Direction.DOWN && f <= floor);
        return onTheWay ? dist : dist + 100;      // penalise turning around
    }
    private void openDoors() { /* notify observers, start door timer */ }
}

}

    All-or-nothing seat lock with expiry

    final class InMemorySeatLock implements SeatLockProvider {
    private record Lock(String user, Instant expiry) {}
    private final Map<String, Map<String, Lock>> locks = new ConcurrentHashMap<>();
    private final Duration ttl; private final Clock clock;
    InMemorySeatLock(Duration ttl, Clock clock) { this.ttl = ttl; this.clock = clock; }

    public boolean lock(String show, List<String> seats, String user) {
        Map<String, Lock> m = locks.computeIfAbsent(show, k -> new HashMap<>());
        synchronized (m) {                         // serialise per show only
            Instant now = clock.instant();
            for (String s : seats) {
                Lock l = m.get(s);
                if (l != null && l.expiry().isAfter(now) && !l.user().equals(user)) return false;
            }
            for (String s : seats) m.put(s, new Lock(user, now.plus(ttl)));
            return true;
        }
    }
    public void unlock(String show, List<String> seats, String user) {
        Map<String, Lock> m = locks.get(show); if (m == null) return;
        synchronized (m) { seats.forEach(s -> m.computeIfPresent(s, (k, l) -> l.user().equals(user) ? null : l)); }
    }
}

    Simplify debts

    record Transfer(String from, String to, long cents) {}

static List<Transfer> simplify(Map<String, Long> net) {   // + owed, − owes
    PriorityQueue<long[]> cred = new PriorityQueue<>((a, b) -> Long.compare(b[1], a[1]));
    PriorityQueue<long[]> debt = new PriorityQueue<>((a, b) -> Long.compare(b[1], a[1]));
    List<String> ids = new ArrayList<>(net.keySet());
    for (int i = 0; i < ids.size(); i++) {
        long v = net.get(ids.get(i));
        if (v > 0) cred.add(new long[]{i, v}); else if (v < 0) debt.add(new long[]{i, -v});
    }
    List<Transfer> out = new ArrayList<>();
    while (!cred.isEmpty() && !debt.isEmpty()) {
        long[] c = cred.poll(), d = debt.poll();
        long amt = Math.min(c[1], d[1]);
        out.add(new Transfer(ids.get((int) d[0]), ids.get((int) c[0]), amt));
        if (c[1] > amt) cred.add(new long[]{c[0], c[1] - amt});
        if (d[1] > amt) debt.add(new long[]{d[0], d[1] - amt});
    }
    return out;   // at most n − 1 transfers; the true minimum is NP-hard
}

    Optimistic vs pessimistic locking in code New#

    // Pessimistic: hold a lock for the whole read-modify-write
synchronized (account) { account.debit(amount); }

// Optimistic in memory: compare-and-swap loop
AtomicReference<Balance> ref = new AtomicReference<>(start);
while (true) {
    Balance cur = ref.get();
    Balance next = cur.minus(amount);           // immutable value
    if (ref.compareAndSet(cur, next)) break;    // retry if someone else won
}

// Optimistic in the database: version column
// UPDATE accounts SET balance = ?, version = version + 1

    Bounded blocking queue (Python)#

    import threading
from collections import deque

class BoundedBlockingQueue:
    def __init__(self, capacity):
        self.q, self.cap = deque(), capacity
        self.lock = threading.Lock()
        self.not_full = threading.Condition(self.lock)
        self.not_empty = threading.Condition(self.lock)
    def enqueue(self, x):
        with self.not_full:
            while len(self.q) == self.cap:      # while, not if: spurious wake-ups
                self.not_full.wait()
            self.q.append(x)
            self.not_empty.notify()
    def dequeue(self):
        with self.not_empty:
            while not self.q:
                self.not_empty.wait()
            x = self.q.popleft()
            self.not_full.notify()
            return x

    Package layout#

    app/

    Evaluation rubric#

    • Runs end-to-end on the sample input
    • Separation of concerns; no god class
    • Extensible: a new type means a new class
    • Meaningful names, small methods, no dead code
    • Edge cases and errors handled explicitly
    • Thread-safety called out where state is shared
    • Tests or a demo that proves behaviour

    API and method design#

    • Methods are verbs in domain language: reserve(), settle().
    • Return domain objects or results, never raw maps.
    • Validate inputs at the boundary; constructors enforce invariants.
    • Prefer immutable inputs and outputs (records, frozen dataclasses).
    • Idempotent where retries are possible: pass a request ID.
    • Pagination and filtering for list methods.

    Errors and edge cases#

    • Domain exceptions (SeatUnavailable, InsufficientFunds) over generic ones.
    • Decide: exception, Optional, or result type. Be consistent.
    • Check: empty input, duplicates, not found, capacity full, invalid transition, concurrent conflict, partial failure.
    • Roll back or compensate on partial failure; never leave half-updated state.

    Testing the design#

    • DIP pays off here: inject fakes for clock, repository, payment gateway.
    • Unit-test each strategy and each state transition.
    • Table-driven tests for rules (fees, splits, discounts).
    • Concurrency test: N threads booking one seat → exactly one succeeds.
    • Say which tests you would write even if time runs out.
